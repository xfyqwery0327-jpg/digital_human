# 讲解员显存与 TTS 测试报告

日期：2026-10-19  
机器：本机 RTX 4090 D，整卡 24564 MiB  
范围：数字讲解员 `server9` 的问答播报。模式 2 只念固定讲稿，模式 3 由大模型写 150～200 字再合成。

## 结论

CosyVoice3 和 Qwen3-TTS 在模式 2、模式 3 下都能把一轮讲完，并收到 `tts_end`。4B 与 8B 的讲稿长度、音频时长接近，4B 够用。

显存上涨发生在讲解员进程，不在大模型进程。Qwen3-TTS 按「一批几句 × 最长那句」向 PyTorch 要激活显存。对象释放后，缓存分配器仍把这块留在显卡上，所以 `nvidia-smi` 只升不降。这不是每问固定多占几十 MB 的张量泄漏，也不是 Gradio 会话。

处理方式：一轮合成结束、等播放的时候调用 `gc.collect()` 和 `torch.cuda.empty_cache()`，把已经没人引用的块还给驱动。句与句之间不调。改完后连续 9 句，每句讲完整卡都回到 9634–9635 MiB。

## 显存现象

看的是整卡 `nvidia-smi`，不是单个进程。4B 专用显存稳定在约 3387–3389 MB，不随问句上涨。上涨都在 8848 的 Qwen 进程。

原因：talker 28 层、8 个 KV head、head_dim 128。`QWEN_TTS_BATCH` 默认 8，拼句上限 `TTS_MERGE_CHARS` 默认 40。第一次出现「8 句一批且最长句更长」时，分配器按这个形状留下一块。同一形状再问不涨。参考音只建一次。`AudioCache` 在 CPU，最多 100 条。

未加 `expandable_segments` 时，整卡曾从 16757 MiB 抬到 17521 MiB（+764），触发点是 8 句一批、最长 32 字、`budget=176`。

`deploy/start-server.ps1` 在未设置时写入 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`。加载日志确认 `alloc=expandable_segments:True`。重启后刚加载整卡 9833 MiB。四句新问题后停在 13758 MiB：第一问是真正的工作集，后三问只再加约 140 MiB。同一档尺寸不再一问抬一截，但更长的 8 句批仍会再要一块新的，要完就留着。

随后 3 轮 × 3 句（模式 3，当时还没有按轮释放）：

| 阶段 | 整卡 |
| --- | --- |
| 开测 | 13519 MiB |
| 第 1 轮三句 | 一直 13519 MiB |
| 第 2 轮第 1 句（8 句一批，最长 24 字） | 15105 MiB（+1586） |
| 第 2 轮第 2 句（8 句一批，最长 30 字） | 16640 MiB（+1535） |
| 第 2 轮第 3 句到第 3 轮结束 | 16570–16634 MiB |

净增 2115 MiB，集中在两句新的更长批次。第 3 轮不再涨。空闲十余分钟只从 13662 MiB 掉到 13560 MiB，不会自己回到模型加载后的水位。

## 对照过的常见原因

| 说法 | 本次情况 |
| --- | --- |
| 批量生成中间状态被缓存 | 对得上。波形已经是 CPU 上的 PCM，驱动仍显示那块激活显存。不是每问固定 +80 MB。 |
| 流式缓冲没关 | 合成使用 `non_streaming_mode=True`，官方返回整段波形。健康检查里 `tts_stream=false`。 |
| 参考音 Tensor 留在计算图上 | 参考音只建一次。缓存前已 `detach`。它算在稳定的约 2114 MiB 活跃显存里。 |
| Gradio session | 讲解员是 FastAPI。`qwen-tts` 会带上 Gradio 依赖，本进程没有启动 Gradio。 |
| 超过 500 字的单次输入 | 拼句上限 40 字，codec token 封顶 1024。实测讲稿按标点拆成 8–14 句。 |
| 改成 eager 注意力 | 已是 bfloat16 + sdpa。eager 更慢，不解决缓存不归还。 |

`qwen-tts==0.1.1` 把 `transformers` 升到 4.57.3。本机没有 SoX 可执行文件，加载时有警告，合成仍成功。`onnxruntime` 仍是 1.18.0 的 CPU 包，没有换成 `deploy/requirements-robot.txt` 里的 `onnxruntime-gpu==1.23.2`。

## 改动

一轮讲完、GPU 已经空闲、客户端还在播已推送的 PCM 时，归还缓存。下一批还要用同样大小的块，所以不放在句与句之间。

- `server9/tts/qwen.py`：`release_cuda_cache()`。先回收 Python 对象并清掉 talker 上的 RoPE / KV，再在「保留显存 − 已分配」超过 64 MiB 时调用 `empty_cache()`。日志记下 active、alloc、reserved。参考音条目在写入缓存前 `detach`。
- `server9/robot/stream.py`：机器人一轮推流结束、等播完再发 `tts_end` 的这段时间里调用。
- `server9/ws/tts.py`：游客 WebSocket 一轮结束时同样调用，异常收尾也调用。
- `deploy/start-server.ps1`：未设置时补上 `expandable_segments:True`。

权重和参考音继续留在显存里。`empty_cache` 清的是缓存分配器里的空块，清不掉仍被模型握住的张量。

## CosyVoice2 / CosyVoice3

两种 CosyVoice 都有同一类缓存，没有 Qwen 那种按 8 句一批往上抬的幅度。

一句算完后，波形已经 `detach` 到 CPU，当句的 token、HiFT、flow 缓存会从模型字典里删掉。参考音和音色向量是按人设留着的，不是按问句增长。PyTorch 仍把这一句用过的最大空闲块留在显卡上，所以不调用 `empty_cache` 的话，整卡讲完不会回到加载水位。CosyVoice2 按 hop 流式声码，单句工作集更小。CosyVoice3 一句只跑一次 flow + HiFT，单句工作集更大，但代码里已经不用「每跳重跑整段」的流式声码。

`server9/tts/cuda_cache.py` 统一处理三种引擎：

- 一轮问答结束、等播放时：空闲缓存超过 64 MiB 就 `empty_cache()`。
- 句与句之间：只有整卡剩余不足 2GB 才清。这次测试剩余大约 18GB，句间没有触发。

大模型仍是 4B。每种声音各 3 组 3 句，模式 3。

CosyVoice3，9/9 通过。加载后整卡 11374 MiB。合成时最高约 11856–12575 MiB，每句讲完回到 11066–11183 MiB。进程里 active 一直是 3333 MiB，reserved 每次回到 3500 MiB。

CosyVoice2，正式 9/9 通过。加载后整卡 10712 MiB，释放后的空闲水位约 10435 MiB。合成时最高约 11023–11697 MiB，九句讲完都回到 10435–10464 MiB。active 一直是 2528 MiB，reserved 每次回到 2728 MiB。第一次用 150 秒超时去等时，第一句音频有 157 秒，客户端先超时了；服务端那句仍然在讲完后把 reserved 从 3684 MiB 还到 2728 MiB。加长到 240 秒后九句都收到了 `tts_end`。

## 还要注意

- 一句还在合成时，整卡仍会升到 1.1 万～1.4 万 MiB。释放发生在这一轮的最后一次合成之后。
- 减小 `QWEN_TTS_BATCH` 只能压低以后的峰值，不能清掉已经占住的块。
- 重启 8848 会立刻清掉该进程的缓存。大模型在另一个进程，不受这次 `empty_cache` 影响。
